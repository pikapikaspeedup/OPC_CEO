# OPC 用户使用场景需求手册与评审

日期：2026-05-18

## 一、打开 OPC 与每日总览

- [支持] 作为 CEO，我希望打开系统后先看到公司当前状态，包括待审批、风险项目、活跃任务、调度状态和部门准备度，方便快速判断今天是否有异常。
- [支持] 作为 CEO，我希望在同一个首页看到部门、项目、系统状态和最近信号，不需要先进入运维页或项目页才能知道公司是否正常运转。
- [不支持] 作为 CEO，我希望打开 CEO Office 后可以直接继续最近一次 CEO 对话，历史消息和发送框默认可见，而不是先看到一个指令入口再展开线程。
- [不支持] 作为 CEO，我希望首页能同时回答“现在公司怎么样”和“我接下来要和系统聊什么”，而不是把运营总览和聊天工作区拆成两个互相抢主视图的区域。

## 二、CEO 持续对话

- [不支持] 作为 CEO，我希望 CEO Office 的核心区域就是一个完整聊天对话框，包含历史内容、发送框、运行状态和错误反馈，适合长时间停留。
- [不支持] 作为 CEO，我希望发送框始终贴近对话历史，输入、发送、等待回复、追问都发生在同一个大方的聊天面板里。
- [支持] 作为 CEO，我希望可以创建 CEO 线程并发送第一条指令。
- [支持] 作为 CEO，我希望在已有 CEO 线程中继续发送消息。
- [支持] 作为 CEO，我希望在对话里选择模型和执行模式，用于区分普通咨询、规划执行和更重的任务。
- [不支持] 作为 CEO，我希望不需要点击“查看线程”或“打开完整线程”才能看到完整对话过程。
- [不支持] 作为 CEO，我希望聊天历史不被小高度容器截断，长回复、工具调用、审批提示和错误都能自然阅读。
- [不支持] 作为 CEO，我希望对话框不仅能执行命令，也能承担澄清、追问、复盘和决策记录。

## 三、CEO 线程历史

- [支持] 作为 CEO，我希望看到最近的 CEO 线程，并能快速切换。
- [不支持] 作为 CEO，我希望在 CEO Office 内浏览完整 CEO 线程历史，而不是只看到少量最近线程。
- [不支持] 作为 CEO，我希望搜索历史 CEO 线程，按主题、项目、部门或最近活动找到过去的讨论。
- [不支持] 作为 CEO，我希望 CEO 线程是 CEO Office 的一等状态，刷新、回退或分享页面时能保留当前线程上下文。
- [不支持] 作为 CEO，我希望新建线程、切换线程和继续线程都发生在同一个聊天工作台里，而不是在 CEO Office 与独立 Chat 页面之间跳转。

## 四、下达任务与跟踪执行

- [支持] 作为 CEO，我希望通过自然语言创建 ad-hoc project。
- [支持] 作为 CEO，我希望通过自然语言创建 scheduler job。
- [支持] 作为 CEO，我希望把任务路由到目标部门。
- [支持] 作为 CEO，我希望看到活跃任务数量，并能知道公司是否正在执行工作。
- [不支持] 作为 CEO，我希望在聊天里下达任务后，任务、项目、运行状态和后续追问形成同一个连续上下文。
- [不支持] 作为 CEO，我希望从聊天回复直接进入相关项目、run、部门或审批对象，然后返回同一个对话继续追问。
- [不支持] 作为 CEO，我希望对运行中的任务进行追问或干预时，不需要切换到另一个独立工作区。

## 五、决策、审批与异常处理

- [支持] 作为 CEO，我希望看到待处理决策、审批数量和风险项目。
- [支持] 作为 CEO，我希望从 CEO Office 进入审批或决策处理。
- [支持] 作为 CEO，我希望看到最近信号，快速发现系统异常、项目变化或运营事件。
- [不支持] 作为 CEO，我希望审批、风险、异常可以作为对话上下文进入聊天面板，让我直接问“这个为什么需要我处理”。
- [不支持] 作为 CEO，我希望在处理审批或决策时，相关对话历史、系统建议和执行结果在同一个工作台里连续呈现。
- [不支持] 作为 CEO，我希望系统在对话中主动解释决策对象、影响范围和下一步，而不是只给我一个外部入口。

## 六、部门与项目运营

- [支持] 作为 CEO，我希望看到部门运行概况，包括部门项目、完成情况、风险和配置状态。
- [支持] 作为 CEO，我希望进入部门详情，查看该部门相关项目和配置。
- [支持] 作为 CEO，我希望进入 OPC 项目看板查看项目、阶段和运行情况。
- [不支持] 作为 CEO，我希望围绕某个部门直接发起对话，例如“研发部今天为什么有风险项目”，并让聊天自动带上该部门上下文。
- [不支持] 作为 CEO，我希望围绕某个项目直接连续追问，例如“这个项目为什么卡住、谁负责、下一步怎么做”，并在同一聊天里看到执行反馈。
- [不支持] 作为 CEO，我希望部门卡片、项目卡片、运行详情和 CEO 对话之间是同一个任务旅程，而不是多个入口之间来回跳。

## 七、知识、记忆与复盘

- [支持] 作为 CEO，我希望从 CEO Office 进入 Knowledge，查看公司的知识资产。
- [支持] 作为 CEO，我希望把知识库作为公司长期资产，而不是只看一次性聊天结果。
- [不支持] 作为 CEO，我希望在 CEO 对话中引用知识资产、历史结论、部门规则或项目复盘，形成可追溯的上下文。
- [不支持] 作为 CEO，我希望一次对话结束后，可以把结论沉淀为知识、规则、SOP 或后续任务。
- [不支持] 作为 CEO，我希望系统能在对话中提示相关知识，而不是让我离开聊天去 Knowledge 页面检索。

## 八、例行运营与自动化

- [支持] 作为 CEO，我希望看到 CEO Routine 的行动项、提醒和状态。
- [支持] 作为 CEO，我希望运行公司循环或查看公司循环摘要。
- [支持] 作为 CEO，我希望看到 scheduler 是否正常。
- [不支持] 作为 CEO，我希望把例行运营动作自然带入聊天，例如“今天的 routine 哪几项没处理，帮我逐项推进”。
- [不支持] 作为 CEO，我希望对自动化任务的创建、确认、修改、暂停和复盘都能通过同一对话完成。
- [不支持] 作为 CEO，我希望系统把定时任务、日报、候选改进和公司循环串成一个持续经营节奏，而不是分布在多个模块。

## 九、首次使用与空状态

- [支持] 作为 CEO，我希望系统能识别已有工作区，并提示部门画像是否完整。
- [支持] 作为 CEO，我希望在部门画像未完整时，可以进入部门补齐流程。
- [支持] 作为 CEO，我希望没有 CEO 线程时，可以创建 CEO 线程并开始发送第一条消息。
- [不支持] 作为 CEO，我希望首次打开 CEO Office 时，即使没有历史线程，也能看到完整聊天工作台的空状态和发送框。
- [不支持] 作为 CEO，我希望没有工作区、没有部门、没有模型或 provider 不可用时，页面明确告诉我当前卡在哪一步，并提供能继续推进的动作。
- [不支持] 作为 CEO，我希望首次完成部门画像后，系统能把我带回 CEO 对话，让我直接用新上下文发起公司经营任务。

## 十、对话上下文与对象切换

- [不支持] 作为 CEO，我希望每次对话都能明确当前上下文是公司、部门、项目、run、审批、知识还是系统设置。
- [不支持] 作为 CEO，我希望在聊天工作台里切换上下文，例如从公司总览切到某个部门，再切到某个项目，发送框能自动带上当前对象。
- [不支持] 作为 CEO，我希望在聊天中引用一个项目、run、知识、部门规则或审批对象，并让系统基于该对象继续回答。
- [不支持] 作为 CEO，我希望从右侧运营上下文点选对象后，聊天区能进入围绕该对象的连续讨论，而不是仅跳转页面。
- [不支持] 作为 CEO，我希望当上下文发生切换时，系统能保留原对话历史，并清楚显示当前问题会作用到哪个对象。

## 十一、从信号到行动再到复盘

- [支持] 作为 CEO，我希望看到最近信号、风险项目、活跃任务和待审批数量。
- [不支持] 作为 CEO，我希望点开一个信号后，可以直接在对话里问原因、影响和建议动作。
- [不支持] 作为 CEO，我希望接受建议动作后，系统能在同一个对话里创建任务、跟踪执行、等待结果并解释结果。
- [不支持] 作为 CEO，我希望任务完成后，系统能回到同一条 CEO 对话里给出复盘和后续建议。
- [不支持] 作为 CEO，我希望从异常信号进入行动后，最终能沉淀为知识、规则、SOP、scheduler 调整或新的 follow-up 任务。
- [不支持] 作为 CEO，我希望系统能清楚显示一个经营事件已经处于“已解释、已行动、已复盘、已沉淀”的哪个阶段。

## 十二、跨会话与长期经营记忆

- [支持] 作为 CEO，我希望历史 CEO 线程能保留下来，并按最近活动展示。
- [不支持] 作为 CEO，我希望系统记住上一次 CEO 对话里的未完成事项，并在下一次打开时继续推进。
- [不支持] 作为 CEO，我希望跨线程追踪同一个项目、部门或问题，不需要靠我手动回忆上次聊到哪里。
- [不支持] 作为 CEO，我希望系统能区分一次性聊天结论、长期公司记忆、部门规则和可执行 SOP。
- [不支持] 作为 CEO，我希望长期经营记忆能反过来影响后续对话、任务路由和自动化建议。

## 十三、权限、确认与高风险动作

- [支持] 作为 CEO，我希望看到待审批事项，并进入审批处理。
- [不支持] 作为 CEO，我希望在聊天中触发高风险动作时，系统能在原对话里请求确认，而不是把确认动作散落到另一个入口。
- [不支持] 作为 CEO，我希望审批前看到动作对象、影响范围、风险原因和可撤销性。
- [不支持] 作为 CEO，我希望批准、拒绝或要求修改后，系统能把决策结果写回同一条对话，并继续执行后续步骤。
- [不支持] 作为 CEO，我希望系统能区分普通咨询、低风险执行、高风险执行和需要人工 gate 的动作。

## 十四、移动端与窄屏使用

- [支持] 作为 CEO，我希望在窄屏下仍能打开 CEO Office 并访问主要导航。
- [不支持] 作为 CEO，我希望移动端也有完整聊天体验，历史内容和发送框不会被折叠、截断或隐藏在次级入口里。
- [不支持] 作为 CEO，我希望移动端优先保留“对话 + 当前状态”，而不是把多个指标、快捷入口和面板顺序堆叠在聊天之前。

## 十五、恢复、错误与可信反馈

- [支持] 作为 CEO，我希望发送失败时看到错误反馈。
- [支持] 作为 CEO，我希望在运行中可以取消当前对话执行。
- [不支持] 作为 CEO，我希望发送失败后能在原输入上下文里快速重试。
- [不支持] 作为 CEO，我希望系统明确区分“消息已发送”“任务已创建”“任务正在执行”“任务已完成”和“需要我审批”。
- [不支持] 作为 CEO，我希望刷新页面后回到同一个 CEO 对话和同一处阅读位置。
- [不支持] 作为 CEO，我希望网络断开、provider 不可用、模型额度不足、任务超时或后台进程异常时，系统能把错误放回当前旅程里解释，而不是只显示一次性错误文本。
- [不支持] 作为 CEO，我希望失败后可以选择重试、换模型、降级为咨询、取消任务或保存为待办。

## 十六、评审结论

- [支持] 作为 CEO，我已经可以把 OPC 当作公司状态看板使用。
- [支持] 作为 CEO，我已经可以从 CEO Office 发起任务、查看关键状态、进入审批、项目、知识和运维相关页面。
- [不支持] 作为 CEO，我还不能把 CEO Office 当作主要聊天工作台使用。
- [不支持] 作为 CEO，我还不能在一个连续对话里完成“查看状态、下达任务、确认执行、处理异常、沉淀结论”的完整经营闭环。
- [不支持] 作为 CEO，我还不能把线程历史、运营上下文、执行反馈和决策动作自然组合成一个统一旅程。
- [不支持] 作为 CEO，我还不能把 OPC 理解为一个“持续经营对话系统”；当前更接近“运营仪表盘 + 指令入口 + 多个跳转页”。
- [不支持] 作为 CEO，我还不能把首次使用、日常经营、异常处理、复盘沉淀和长期记忆串成一个完整产品闭环。

## 十七、下一版体验目标

- [不支持] 作为 CEO，我希望下一版 CEO Office 默认呈现完整聊天工作台，并把运营状态作为对话上下文侧栏。
- [不支持] 作为 CEO，我希望下一版保留 OPC 总览能力，但总览不应压过持续对话。
- [不支持] 作为 CEO，我希望下一版线程历史、当前消息、发送框、运行状态和关键业务上下文在同一屏形成稳定布局。
- [不支持] 作为 CEO，我希望下一版所有 CEO 关键旅程都能从对话开始，也能回到对话结束。
- [不支持] 作为 CEO，我希望下一版能覆盖从首次配置、日常问答、任务派发、异常处理、审批确认、完成复盘到知识沉淀的完整旅程。

### 18.3 每主题的 DoD（完成定义）

#### 主题 A：CEO Office 改造为聊天主工作台
- [ ] 默认主视图为聊天工作台，运营总览作为可折叠侧栏（默认折叠 / 可置顶切换）
- [ ] 历史消息、发送框、运行状态、错误反馈在同一容器内不被截断
- [ ] 刷新页面后回到原线程、原阅读位置
- [ ] 桌面与移动端均默认聊天为主视图
- [ ] 不再需要点击"查看线程 / 打开完整线程"

#### 主题 B：对话上下文对象化
- [ ] `thread.context` 数据模型支持 `{type: company|department|project|run|approval|knowledge, refId, snapshotAt}`
- [ ] 发送框始终显示当前上下文对象（chip 形式可点击/可移除）
- [ ] 支持 `@` mention 与侧栏拖入两种方式引用对象
- [ ] 切换上下文不丢失原对话历史
- [ ] 工具调用、回答、复盘均能基于该对象返回结果

#### 主题 C：信号→行动→复盘单线程旅程
- [ ] 点开任意信号可"进入对话"，自动带上信号上下文
- [ ] 接受建议动作 → 同一线程内创建任务 → 跟踪 run → 回写结果 → 自动给出复盘
- [ ] 每个经营事件在 UI 上明确显示阶段：`已解释 / 已行动 / 已复盘 / 已沉淀`

#### 主题 D：跨会话长期记忆
- [ ] 区分三类记忆：`session conclusion` / `company memory` / `department rule` / `executable SOP`
- [ ] 打开新线程时主动列出"上次未完成事项"
- [ ] 跨线程按项目/部门/问题维度可追踪
- [ ] 长期记忆能影响：后续对话提示、任务路由、自动化建议

#### 主题 E：审批/高风险动作内联确认
- [ ] 高风险动作触发后，在原对话内弹出 confirm 卡（不跳页）
- [ ] confirm 卡展示：对象、影响范围、风险原因、可撤销性、推荐处理
- [ ] 批准/拒绝/要求修改 → 决策写回同一线程并继续执行
- [ ] 风险等级判定服务覆盖全部工具调用（见 §十九）

#### 主题 F：错误与恢复的旅程化
- [ ] 发送失败：原输入保留，提供"重试 / 换模型 / 降级为咨询 / 取消 / 存为待办"五种动作
- [ ] 区分 6 类错误码：`network / provider_unavailable / quota / timeout / tool_error / unknown`
- [ ] 错误以"旅程内的一步"呈现，不弹独立 toast
- [ ] 刷新后 scroll anchor 恢复

#### 主题 G：例行自动化对话化
- [ ] `routine` 行动项可一键"逐项推进"，自动派发到当前线程

## 十九、高风险动作判定矩阵

补 §十三·116 的空白。系统在执行任意工具调用 / 任务派发前，按矩阵分级并决定是否需要 in-chat 人工 gate。

### 19.1 风险等级定义

| 等级 | 名称 | 处理策略 |
|---|---|---|
| L0 | 纯咨询 | 自动执行，无确认 |
| L1 | 低风险执行 | 自动执行，结果回写线程 |
| L2 | 中风险执行 | in-chat 软确认（5 秒倒计时可撤回） |
| L3 | 高风险执行 | in-chat 硬确认（必须主动批准） |
| L4 | 强制人工 gate | 必须经审批通道 + 二次确认 |

### 19.2 判定规则（按维度打分，取最高）

| 维度 | L0 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|---|
| 可撤销性 | 完全可撤销 | 易撤销 | 需补偿 | 不可撤销 | 不可撤销且影响外部 |
| 影响范围 | 仅当前对话 | 单对象/单 run | 单部门 | 多部门/全公司 | 外部用户/客户/合作方 |
| 费用 | 0 | < $1 | < $10 | < $100 | ≥ $100 或不可预测 |
| 数据写入 | 只读 | 创建草稿 | 修改业务数据 | 删除/批量改写 | 删除生产数据/审计记录 |
| 外部副作用 | 无 | 内部通知 | 内部任务派发 | 外部 API 调用 | 发送给客户/合作方 |
| 时间窗口 | 即时可逆 | 当日可逆 | 当周可逆 | 不限 | 不可逆 |

**示例**：
- 查询活跃任务数 → L0
- 创建一个 ad-hoc project 草稿 → L1
- 把任务派发到研发部并启动 run → L2
- 删除一个 scheduler job → L3
- 给客户发送邮件 / 修改线上配置 → L4

### 19.3 in-chat 确认卡必备字段

```
┌─ 高风险动作确认 ─────────────────┐
│ 动作：删除 scheduler job "daily-report"
│ 对象：scheduler.job#42
│ 影响范围：研发部 + 运维部（订阅者 8 人）
│ 风险原因：删除后历史 run 记录保留但不再触发
│ 可撤销性：✗ 不可撤销（需重新创建）
│ 推荐处理：先暂停 24h 观察 → 再删除
│ ─────────────────────────────
│ [批准]  [修改]  [改为暂停]  [取消]
└─────────────────────────────────┘
```

## 二十二、对话内对象引用与上下文协议

补 §十·89 的交互空白。

### 22.1 引用方式

| 方式 | 触发 | 场景 |
|---|---|---|
| `@` mention | 输入框打 `@` 触发对象选择器 | 主动引用已知对象 |
| 侧栏拖入 | 从运营上下文侧栏拖到发送框 | 浏览中发现想讨论的对象 |

### 22.2 引用渲染规范

- 输入框内：chip 形式，可点击展开预览，可 × 移除
- 历史消息内：超链接 + 悬停预览卡
- 多对象引用：在发送框上方以 chip 列表呈现，超过 3 个折叠为"+ N more"

### 22.3 上下文协议（thread.context）

```typescript
type ThreadContext = {
  primary: ContextRef           // 当前主要对象
  references: ContextRef[]      // 本条消息引用到的其它对象
  inheritedFrom?: ThreadContext // 从上一条消息继承的上下文（可被覆盖）
}

type ContextRef = {
  type: 'company' | 'department' | 'project' | 'run' | 'approval' | 'knowledge' | 'signal'
  refId: string
  snapshotAt: string  // ISO 时间戳，用于"对象在被引用时的状态"
  label: string
}
```

## 二十四、多端/多标签状态一致性

补 §十二 的空白。

- **单一真相源**：线程状态以服务端 `thread.version` 为准，客户端订阅 WebSocket 增量。

## 二十七、风险与回滚预案

| 风险 | 影响 | 应对 |
|---|---|---|
| 聊天主视图反而降低运营总览效率 | CEO 抱怨"看不到全局" | 提供"经典布局"开关；监测总览停留时长；必要时调整侧栏默认展开 |
| 上下文对象化导致后端工具调用复杂度上升 | 工具响应变慢、出错率上升 | 主题 B 单独压测；工具层加 context 容错；分批接入工具 |
| 内联审批被误批 | 高风险动作误执行 | L3/L4 必须二次确认；保留 5 分钟撤销窗口；审计日志可追溯 |
| 长期记忆污染对话 | 系统过度自信、产生错误建议 | 记忆显式可见、可编辑、可删除；区分"事实"与"推断"；提供"忽略本条记忆"动作 |
| 移动端性能不足 | 移动端卡顿、用户流失 | 主题 H 单独性能预算；超长线程自动摘要 |
| 灰度期间数据模型变更 | 旧线程上下文丢失 | thread.context 增量迁移、保留旧字段 30 天；线上回滚开关 |

**回滚触发条件**：任一阶段上线后，北极星指标连续 3 天回退 ≥ 10%，或 P0 缺陷影响 ≥ 5% 用户，立即回滚到上一阶段。
